## このチャプターで何をするか

学習を始める前に「道具の準備」をします。Snowflakeには複数の操作方法があり、
このカリキュラムでは以下の3つを使います。

| ツール | 何ができるか | いつ使うか |
|---|---|---|
| **Snowsight** | ブラウザからSQL実行・GUIでデータ確認 | 普段のSQL実行・結果確認 |
| **SnowSQL** | コマンドラインからSQL＋ファイルアップロード | ローカルCSVのアップロード（PUTコマンド）時 |
| **Python** | プログラムからSnowflakeを操作・自動化 | バッチ処理・ループ処理・自動化 |

> 💡 **なぜ3種類も使うのか？**
> SnowsightはファイルアップロードのPUTコマンドをサポートしていません。
> PUTはSnowQLまたはPythonからしか実行できないため、
> 用途に合わせて使い分けます。

## 0-1 Snowsightにログイン

> 💡 **Snowsightとは？**
> Snowflakeが提供するWebブラウザ上のGUI管理コンソールです。
> ここからSQLの実行、データのプレビュー、実行履歴の確認などができます。
>
> **やらないと？** Snowflakeを操作する手段がなく、何もできません。
> **やると？** ブラウザだけで完結するSQL実行環境が手に入ります。

1. https://app.snowflake.com にアクセス
2. アカウントURLを入力してログイン
3. 左メニュー「Worksheets」を開き、新規ワークシート作成
4. 下記の動作確認クエリを実行：

```sql
-- 現在ログインしているユーザー、ロール、使用中のウェアハウスを確認
-- これが返ってくれば接続成功
SELECT CURRENT_USER(), CURRENT_ROLE(), CURRENT_WAREHOUSE();
```

## 0-2 SnowSQL（CLI）のインストール（Windows）

> 💡 **SnowSQLとは？**
> Snowflakeの公式コマンドラインツールです。
> ターミナルからSQLを実行できるほか、**ローカルファイルのアップロード（PUTコマンド）**
> が使えます。PUTはSnowsightからは実行できないため、SnowSQLが必要です。
>
> **やらないと？** ローカルのCSVファイルをSnowflakeに送る手段がなくなります。
> **やると？** コマンド1行でCSVをSnowflakeにアップロードできます。

1. https://docs.snowflake.com/en/user-guide/snowsql-install-config からインストーラをDL
2. インストール後、コマンドプロンプトで確認：

```cmd
rem インストールが成功していればバージョン番号が表示される
snowsql --version
```

3. 接続テスト（アカウント識別子はSnowsightのURLから確認できます）：

```cmd
rem -a: アカウント識別子（例: abc12345.ap-northeast-1.aws）
rem -u: Snowflakeのユーザー名
snowsql -a <アカウント識別子> -u <ユーザー名>
```

## 0-3 Python環境の準備

> 💡 **なぜPythonライブラリが3種類あるのか？**
> 役割が異なるため、それぞれ必要です。
>
> | ライブラリ | 役割 |
> |---|---|
> | `snowflake-connector-python` | SQLの実行・PUTコマンド（基本接続） |
> | `snowflake-snowpark-python` | Python内でSQL的な処理をDataFrame APIで書く |
> | `snowflake[core]` | DB・スキーマ・タスクなどのオブジェクトをPythonから管理 |
>
> **やらないと？** PythonからSnowflakeに接続できません。
> **やると？** バッチ処理や自動化をPythonスクリプトとして組めます。

```cmd
rem 基本接続ライブラリ（SQLの実行・PUTコマンド）
pip install snowflake-connector-python

rem DataFrameAPIでSQL的な処理を書くためのSnowpark
pip install snowflake-snowpark-python

rem DB・テーブル・タスクなどをPythonオブジェクトとして管理するAPI
pip install "snowflake[core]"
```

動作確認（Python）：

```python
import snowflake.connector

# Snowflakeへの接続情報
conn = snowflake.connector.connect(
    account="<アカウント識別子>",  # 例: abc12345.ap-northeast-1.aws
    user="<ユーザー名>",           # Snowflakeのログインユーザー名
    password="<パスワード>",       # 本番では環境変数や秘密管理ツールを推奨
    warehouse="COMPUTE_WH",        # クエリ実行に使うウェアハウス名
    database="<DB名>",             # 接続先データベース名
    schema="PUBLIC"                # 接続先スキーマ名
)

cur = conn.cursor()
cur.execute("SELECT CURRENT_VERSION()")  # Snowflakeのバージョンを取得
print(cur.fetchone())                    # 結果を1行取得して表示
conn.close()                             # 接続を閉じる（接続は課金対象ではないが後始末として必須）
```

## 0-4 学習用DB・スキーマの作成（Snowsight）

> 💡 **なぜ学習専用のデータベースを作るのか？**
> 業務用のDBと混在させると、誤ってデータを上書き・削除するリスクがあります。
> 学習専用DBを作ることで安全に練習できます。
>
> **やらないと？** 既存のDBに誤って影響を与える危険があります。
> **やると？** 失敗しても影響範囲が学習用DBに限定されるので安心です。

> 💡 **なぜ Bronze / Silver / Gold の3層に分けるのか？（重要）**
> これはデータエンジニアリングの定番パターン「**メダリオンアーキテクチャ**」です。
>
> | 層 | 役割 | データの状態 |
> |---|---|---|
> | **Bronze** | 生データをそのまま保存 | 加工なし・元データを保全 |
> | **Silver** | クレンジング・正規化済み | NULL除去・外れ値処理済み |
> | **Gold** | 集計・分析用に最適化 | レポート・ダッシュボード向け |
>
> **やらないと？** 生データと加工済みデータが混在し、「どのデータが正しいか」が
> わからなくなります。エラーが起きたときの原因調査も困難になります。
>
> **やると？** 各層の責任が明確になり、問題が起きた層だけ修正できます。
> また、Bronzeを保持しているのでいつでも再処理可能です。

```sql
-- 学習専用データベースを作成（既に存在してもエラーにならない）
CREATE DATABASE IF NOT EXISTS SENSOR_LAB;

-- 3層アーキテクチャ用スキーマ（BronzeはDB名.スキーマ名の形式）
CREATE SCHEMA IF NOT EXISTS SENSOR_LAB.BRONZE;  -- 生データ置き場
CREATE SCHEMA IF NOT EXISTS SENSOR_LAB.SILVER;  -- クレンジング済みデータ
CREATE SCHEMA IF NOT EXISTS SENSOR_LAB.GOLD;    -- 集計・レポート用データ

-- 以降のSQL実行のデフォルトコンテキストを設定
USE DATABASE SENSOR_LAB;
USE SCHEMA BRONZE;
```
